# Offline version changer

For trusted dedicated rootless Docker/Podman instances only. Enable --allow-fleet-versions on the connector. Stop the server, verify an independent complete server backup, check Java/plugin compatibility and accept Minecraft EULA. Enter an exact newer numeric release of the same software (Vanilla, Paper or Purpur). The existing provider resolver selects a stable artifact and verifies its published digest (SHA-1 for Vanilla, SHA-256 for Paper, MD5 for Purpur); OMCP also records a local SHA-256. These checks establish consistency, not code safety.

The connector verifies the old JAR against existing provenance, stages the new JAR and receipt, retains one old JAR and its provenance under .omcp-previous-version-<instance UUID> in the private fleet root, and writes a durable pending marker before replacing files. It never edits worlds, plugins, or server settings during the upgrade and never starts automatically. The admin must finalize a successful receipt before the panel changes the reserved version. Inspect/reconcile can confirm either the old or target version after an interrupted job. An inconsistent JAR/metadata pair fails closed; an operator must stop the connector and ensure the runtime is absent, restore a consistent pair from the retained archive, then inspect and finalize. Do not delete a pending marker as a shortcut. After a verified transition and independent backup, move the retained archive to safe local storage before another upgrade.

No automatic downgrade, software-family migration, Java runtime selection, complete server rollback or world rollback is provided. A newer JAR may change worlds on first boot; reverting just the JAR is not a safe world rollback. Actual provider downloads and Minecraft boots require separate testing. Only trusted offline use with no concurrent local edits.
